`pytest` and `unittest` are both Python testing frameworks, but they differ mainly in syntax, style, and feature set.
`unittest` is Python’s built‑in, class‑based framework, while `pytest` is a third‑party, more flexible runner that focuses on
simplicity and powerful features. [browserstack](https://www.browserstack.com/guide/pytest-vs-unittest)

### 1. Style and syntax

- **`unittest`**:
  - Requires classes inheriting from `unittest.TestCase`.
  - Tests are written as methods (e.g., `test_add`).
  - Uses special assertion methods such as `assertEqual`, `assertTrue`, etc.  
    This style is more verbose and “boilerplate‑heavy” but very structured.
    [geeksforgeeks](https://www.geeksforgeeks.org/software-testing/difference-between-pytest-and-unittest/)

- **`pytest`**:
  - Lets you write tests as simple Python functions.
  - Uses plain `assert` statements (e.g., `assert result == 5`).
  - Reads more like normal Python code and needs less boilerplate.
    [jetbrains](https://www.jetbrains.com/guide/pytest/links/pytest-v-unittest/)

### 2. Fixtures and setup/teardown

- **`unittest`**:
  - Uses `setUp()` and `tearDown()` (and class‑level `setUpClass`/`tearDownClass`) for setup and cleanup.
  - Scope is limited to class or method level. [browserstack](https://www.browserstack.com/guide/pytest-vs-unittest)

- **`pytest`**:
  - Uses **fixtures** (decorated with `@pytest.fixture`) that can be reused across many tests.
  - Fixtures support multiple scopes (`function`, `class`, `module`, `session`) and can be parameterized.  
    This makes shared test data and complex environments much easier to manage.
    [trunk](https://trunk.io/learn/pytest-vs-unittest-a-comparison)

### 3. Test discovery and execution

- **`unittest`**:
  - Discovers tests by scanning classes that inherit from `TestCase` and methods starting with `test`.
  - Often requires explicit test runners or configuration to run suites.
    [geeksforgeeks](https://www.geeksforgeeks.org/software-testing/difference-between-pytest-and-unittest/)

- **`pytest`**:
  - Automatically discovers test files and functions using naming conventions (`test_*.py`, `test_*`, `*_test`).
  - Runs tests with a single command (`pytest`) and gives detailed, readable failure output.
    [builtin](https://builtin.com/data-science/pytest-vs-unittest)

### 4. Extensibility and ecosystem

- **`unittest`**:
  - Part of the standard library, so it’s always available and widely understood.
  - Limited plugin ecosystem compared with `pytest`.
    [jetbrains](https://www.jetbrains.com/guide/pytest/links/pytest-v-unittest/)

- **`pytest`**:
  - Has a rich plugin ecosystem (e.g., coverage, mocking, parameterized tests, async support).
  - Supports parameterized tests easily (`@pytest.mark.parametrize`).
    [j-labs](https://www.j-labs.pl/en/tech-blog/pytest-why-its-more-popular-than-unittest/)

In practice, `pytest` is usually preferred for new projects because it’s more concise and feature‑rich, while `unittest` is
common in older or standard‑library‑focused codebases. [trunk](https://trunk.io/learn/pytest-vs-unittest-a-comparison)
